# ASR-stage levers for Rflow: contextual biasing, decoding settings, model candidates

Context: Rflow uses sherpa-onnx 1.13.8 with `sherpa-onnx-nemo-parakeet-unified-en-0.6b-int8-non-streaming`, greedy decoding, 4 threads. Errors are mostly names and tech terms (commit->clot, Claude->cloud, Tamil->Tamar, SST->STD, polishing->publishing). Research date: 2026-09-30.

## (a) Biasing the ASR toward the user's vocabulary (sherpa-onnx hotwords, NeMo biasing, Whisper prompting)

### Takeaway
sherpa-onnx now supports hotwords (token-level context-graph boosting) for NeMo transducers, including Parakeet TDT and RNN-T, in offline mode. It needs `decoding_method="modified_beam_search"`, `modeling_unit="bpe"` and a `bpe_vocab` file. Rflow's installed 1.13.8 exposes every parameter needed, and hotwords can be passed per stream. This is the strongest ASR-side lever for the "Your words" list. The published docs page is out of date and still says NeMo is not supported. The main practical blocker is obtaining a `bpe.vocab` for the unified model.

### Cited Findings
- PR #3077 adds `OfflineTransducerModifiedBeamSearchNeMoDecoder`: modified beam search plus hotwords/context biasing for NeMo transducers, including TDT (Parakeet). It tracks a per-hypothesis `frame_offset` and TDT durations, and a follow-up commit added duration log-prob to hypothesis scores. csukuangfj merged it on 5 Feb 2026 — [PR #3077](https://github.com/k2-fsa/sherpa-onnx/pull/3077)
- In the PR's Parakeet TDT v2 demo, greedy output "Phebe" became "Phoebe" with hotwords, at RTF ~0.04 on CPU. The PR notes that hotwords require a `bpe.vocab` generated by `generate_bpe_vocab.py` during ONNX export, with a default `hotwords-score` of 1.5 — [PR #3077](https://github.com/k2-fsa/sherpa-onnx/pull/3077)
- CLI usage from the PR: `--decoding-method=modified_beam_search --bpe-vocab=bpe.vocab --modeling-unit=bpe --hotwords-file=hotwords.txt --hotwords-score=1.5` — [PR #3077](https://github.com/k2-fsa/sherpa-onnx/pull/3077)
- CHANGELOG entries: "Add modified beam search and hotwords support for NeMo transducer models" (listed under 1.12.21; pub.dev and other summaries say 1.12.24), a fix for NeMo transducer modified beam search bugs in 1.13.1 (#3589), and "hotwords argument to OfflineQwen3ASRModelConfig" in 1.12.34. Streaming NeMo hotwords came in PR #3895. The exact version number is inconsistent between sources, but every source puts it before 1.13.8 — [CHANGELOG](https://github.com/k2-fsa/sherpa-onnx/blob/master/CHANGELOG.md); [PR #3895](https://github.com/k2-fsa/sherpa-onnx/pull/3895); [pub.dev changelog](https://pub.dev/packages/sherpa_onnx/changelog)
- **Conflict:** the official hotwords docs page still says only the "Offline/Online transducer models" (icefall zipformer family) support hotwords and "all other model types, including NeMo, do not". PR #3077 supersedes this — [sherpa hotwords docs](https://k2-fsa.github.io/sherpa/onnx/hotwords/index.html)
- Docs requirements: `decoding-method` must be `modified_beam_search` because greedy does not support hotwords. `modeling-unit` is `bpe` for English and `bpe-vocab` is needed for bpe. The hotword file has one phrase per line, with an optional per-phrase score as the last item (for example `语音识别 :3.5`). Docs examples show "QUARTER"->"QUARTERS" and "FOR EVER"->"FOREVER" at comparable RTF (0.065-0.208) — [sherpa hotwords docs](https://k2-fsa.github.io/sherpa/onnx/hotwords/index.html)
- A third-party wrapper (react-native-sherpa-onnx) states that hotwords apply to the `transducer` and `nemo_transducer` model types. Given a non-empty hotwords file, the wrapper forces `modified_beam_search` and `maxActivePaths` >= 4 — [react-native-sherpa-onnx docs](https://www.mintlify.com/XDcobra/react-native-sherpa-onnx/advanced/hotwords)
- **Verified locally** in Rflow's `.venv` (sherpa_onnx 1.13.8, `offline_recognizer.py`), the signature is `OfflineRecognizer.from_transducer(encoder, decoder, joiner, tokens, num_threads=1, sample_rate=16000, feature_dim=80, dither=0.0, decoding_method="greedy_search", max_active_paths=4, hotwords_file="", hotwords_score=1.5, blank_penalty=0.0, modeling_unit="cjkchar", bpe_vocab="", debug=False, provider="cpu", model_type="transducer", rule_fsts="", rule_fars="", lm="", lm_scale=0.1, hr_dict_dir="", hr_rule_fsts="", hr_lexicon="", lodr_fst="", lodr_scale=0.0)`. `create_stream(hotwords: Optional[str])` accepts per-stream hotwords separated by `/`, with the tokens inside a hotword separated by spaces. Docstring: modeling_unit "is needed only when hotwords are provided"; bpe_vocab is "the vocabulary generated by google's sentencepiece program ... two columns, token and log probability" — local file `C:\dev\rflow\.venv\Lib\site-packages\sherpa_onnx\offline_recognizer.py`
- **Verified via the HF API:** the `csukuangfj/sherpa-onnx-nemo-parakeet-tdt-0.6b-v2-int8` repo contains only `encoder/decoder/joiner.int8.onnx`, `tokens.txt`, `README.md` and `test_wavs`, with **no bpe.vocab**. The unified model's HF repo returned 401, so its file list is unverified — [HF API v2-int8](https://huggingface.co/api/models/csukuangfj/sherpa-onnx-nemo-parakeet-tdt-0.6b-v2-int8)
- Homophone replacer (`hr_dict_dir`, `hr_lexicon`, `hr_rule_fsts`) is **Chinese-only**: pinyin-based and built with pynini. The docs say there are "no plans" for non-Chinese text, so it is not usable for English. `rule_fsts`/`rule_fars` are ITN FSTs, not biasing — [homophone replacer docs](https://k2-fsa.github.io/sherpa/onnx/homophone-replacer/index.html); local docstring
- NeMo's own biasing, per the NeMo docs:
  - **GPU-PB / TurboBias** (boosting tree, shallow fusion) works with CTC, RNN-T/TDT and AED/Canary, in greedy and beam search. Recommended settings are `context_score` 1.0, `depth_scaling` 2.0 (CTC/RNNT/TDT) or 1.0 (Canary), and a tuned `boosting_tree_alpha`.
  - **CTC-WS** (CTC word spotter) needs hybrid TDT/RNNT-CTC models (params `beam_threshold`, `context_score`, `ctc_ali_token_weight`).
  - **Flashlight** word boosting uses lexicon CTC with KenLM; the recommended boost range is ±20-100.
  - [NeMo word boosting docs](https://docs.nvidia.com/nemo-framework/user-guide/latest/nemotoolkit/asr/asr_customization/word_boosting.html)
- The TurboBias paper (Andrusenko et al., ASRU 2025) reports handling up to 20k key phrases "without noticeable speed degradation", beating open-source biasing methods on accuracy and speed. Numeric gains are not in the abstract — [arXiv 2508.07014](https://arxiv.org/abs/2508.07014)
- The CTC-WS paper (Interspeech 2024) reports faster biasing with improved F-score and WER over baselines, via Hybrid Transducer-CTC. The abstract gives no numbers — [arXiv 2406.07096](https://arxiv.org/abs/2406.07096)
- faster-whisper `transcribe()` docstrings: `initial_prompt` is "Optional text string or iterable of token ids to provide as a prompt for the first window". `hotwords` is "Hotwords/hint phrases to provide the model with. Has no effect if prefix is not None" — [faster-whisper transcribe.py](https://github.com/SYSTRAN/faster-whisper/blob/master/faster_whisper/transcribe.py)

### Inferences
- **Why "beam search was no better":** beam search alone (`max_active_paths` 4) usually changes little on a strong transducer. The gain comes from the hotwords context graph. Hotwords also silently do nothing unless all four are set: `decoding_method="modified_beam_search"`, `modeling_unit="bpe"` (the default is `"cjkchar"`, a pitfall), a valid `bpe_vocab`, and hotwords via `hotwords_file` or `create_stream(hotwords=...)`. The earlier trial likely lacked one of these.
- **Casing pitfall:** Parakeet's BPE is cased and punctuated, unlike the uppercase LibriSpeech zipformer examples in the docs. Hotwords should be written in the exact surface form the model emits ("Claude", "Tamil", "SST", "commit"). Adding a space-prefixed and a sentence-initial variant may also help. This follows from sentencepiece tokenization and was not tested in any source.
- **Getting bpe.vocab:** it is generated from the NeMo tokenizer's sentencepiece model (`generate_bpe_vocab.py` in the sherpa-onnx NeMo export scripts). For the unified model, either download the `.nemo` from `nvidia/parakeet-unified-en-0.6b`, extract `tokenizer.model` and dump the vocab with log-probs, or check whether the GitHub release tarball ships one.
- **Score and settings:** start with `hotwords_score` 1.5 (the default) and per-word `:2.0`–`:3.0` for words that are hard to recognize. Too high a score causes false insertions: "Claude" would appear when the user says "cloud". Keep the list to the user's real words. Per-stream hotwords let Rflow pass the live "Your words" list without rebuilding the recognizer.
- **Expected coverage by error type:**
  - Name/term substitutions are the error type biasing fixes: Claude, Tamil, SST, commit.
  - "polishing->publishing" is an ordinary-word confusion. Boosting "polishing" globally risks side effects, so it is better left to the LLM cleanup step.
- **Speed:** modified beam search with 4 paths costs more than greedy. The PR's RTF ~0.04 suggests it is still fine for dictation, but it should be measured on the owner's laptop.
- **NeMo GPU-PB / CTC-WS** run inside NeMo/PyTorch decoding and are not part of the exported ONNX graphs. They would need PyTorch-on-CPU NeMo inference, which is heavy on Windows. sherpa-onnx's context graph is the practical CPU equivalent.
- **Whisper prompt/hotwords** can prime spellings of names. Commonly reported risks (not verified by a source in this session) are prompt copying and hallucination on silence, plus the effect being limited to the first 30 s window.

### Gaps
- No quantitative WER/recall numbers for sherpa-onnx NeMo hotwords beyond single-utterance examples. TurboBias and CTC-WS numeric gains need the full PDFs.
- Unverified whether the sherpa-onnx parakeet-unified release package includes `bpe.vocab`: the HF repo returned 401 and the Rflow model dir was not found on disk.
- Unverified whether PR #3077's decoder handles the unified model's plain RNN-T. It is described as "NeMo transducer models (including TDT)", so plain RNN-T should be covered.
- No sourced measurements of faster-whisper `hotwords`/`initial_prompt` effectiveness.

## (b) Decoding settings (greedy vs modified beam search, blank_penalty, LM/LODR)

### Takeaway
Keep greedy for the no-vocabulary path. Switch to `modified_beam_search` (max_active_paths 4) only when hotwords are present. `blank_penalty` and LM/LODR are secondary knobs with no sourced evidence for Parakeet.

### Cited Findings
- Hotwords are applied only with `modified_beam_search`, and the default decoding method is `greedy_search` — [sherpa hotwords docs](https://k2-fsa.github.io/sherpa/onnx/hotwords/index.html)
- `max_active_paths` defaults to 4. `blank_penalty` (default 0.0) is "the penalty applied on blank symbol during decoding". `lm`/`lm_scale` (0.1) and `lodr_fst`/`lodr_scale` are exposed for transducers — local `offline_recognizer.py` (1.13.8); [offline-decode-files.py](https://github.com/k2-fsa/sherpa-onnx/blob/master/python-api-examples/offline-decode-files.py)
- The NeMo modified beam search keeps 4 active paths by default — [PR #3077](https://github.com/k2-fsa/sherpa-onnx/pull/3077)

### Inferences
- A positive `blank_penalty` (for example 0.5–1.5) mainly reduces deletions, where words are dropped. It will not fix substitutions like Claude->cloud, so its value here is low.
- A domain LM via `lm` would need an RNN-LM ONNX in sherpa format, which is heavy. The hotword context graph is the lightweight equivalent.
- Suggested A/B:
  1. greedy
  2. MBS with 4 paths and no hotwords
  3. MBS with 4 paths, hotwords, score 1.5
  4. the same at score 2.5

  Measure term recall and false insertions on 30–50 of the owner's recorded clips.

### Gaps
- No published Parakeet-specific tuning for blank_penalty or LM fusion in sherpa-onnx.

## (c) Model candidates: accuracy vs CPU speed, availability in sherpa-onnx, punctuation

### Takeaway
**Parakeet-unified-en-0.6b** (released Apr 2026) is currently the most accurate English Parakeet 0.6B and is already in use. Offline it averages about 5.9% WER on the leaderboard sets, against 6.05% for TDT v2 and about 6.3% for v3. The only clearly more accurate open models are 1.7–2.5B LLM-decoder models: Granite Speech 4.1 2B at 5.33%, Cohere Transcribe at 5.42%, Canary-Qwen-2.5B at 5.63% and Qwen3-ASR-1.7B at 5.76%. They are 10x+ slower, so a model swap is unlikely to fix name errors more cheaply than biasing. Moonshine v2 Medium (6.65%, 245M) is the notable small or streaming option. Whisper large-v3 (7.44%) and turbo are less accurate and slower on CPU than Parakeet, but are prompt-biasable and multilingual (Tamil/Japanese).

### Cited Findings
- **parakeet-unified-en-0.6b** (NVIDIA, HF release 7 Apr 2026):
  - Architecture: unified FastConformer encoder (24 layers) plus an **RNN-T** decoder (not TDT), trained jointly for offline and streaming. Streaming latency is selectable from 2080 ms down to 160 ms in 80 ms steps. Built-in punctuation and capitalization. Trained mostly on about 250k h of Granary English.
  - Offline WER: LS-clean 1.63, LS-other 3.11, SPGI 2.04, TEDLIUM 3.39, GigaSpeech 10.05, Earnings22 11.16, AMI 10.14, VoxPopuli 5.77. Average streaming WER at 160 ms is 8.44%.
  - The card claims it outperforms parakeet-tdt-0.6b-v2 and matches or exceeds nemotron-speech-streaming at latencies up to 240 ms.
  - [HF model card](https://huggingface.co/nvidia/parakeet-unified-en-0.6b); [NVIDIA via search summary](https://huggingface.co/nvidia/parakeet-unified-en-0.6b)
- **parakeet-tdt-0.6b-v2:** average leaderboard WER 6.05% and RTFx 3386 at batch 128 on GPU. Punctuation, capitalization and word timestamps. Up to 24 min in a single pass with full attention; local attention is available for longer audio — [HF model card](https://huggingface.co/nvidia/parakeet-tdt-0.6b-v2)
- **parakeet-tdt-0.6b-v3:** 25 European languages, WER 6.32% and RTFx 3332.74 — [MarkTechPost 2026 comparison](https://www.marktechpost.com/2026/07/23/best-open-speech-recognition-asr-models-in-2026-wer-languages-latency-and-license-compared/)

### Inferences
- **Parakeet-unified is already the right English Parakeet.** Estimated from the card numbers, its offline average is about (1.63+3.11+2.04+3.39+10.05+11.16+10.14+5.77)/8 ≈ **5.91%**. That puts it just above TDT v2 (6.05%) and v3 (about 6.3%) and within about 0.3–0.6 points of the 2B LLM-decoder models. Switching to TDT v2 or v3 would not improve English accuracy. v3 is only worth it for European languages, and it does not cover Tamil or Japanese.
- **Unified's RNN-T decoder:** the unified model uses plain RNN-T, so it emits a token decision on every frame. TDT can skip frames, so the TDT models may decode a bit faster on CPU. The sherpa docs also note better RTF for TDT. That fits Rflow's 3 min taking about 23 s (RTF about 0.13).
- **LLM-decoder models** (Granite 4.1 2B, Canary-Qwen-2.5B, Cohere 2B, Qwen3-ASR-1.7B) gain about 0.3–0.6 WER points on average. Their autoregressive decoders are likely 5–20x slower than the current setup on a CPU laptop. Their ability to be prompted or biased (for example the Qwen3-ASR hotwords arg in sherpa-onnx) is interesting for names, but no CPU latency figures were found.
- **For Tamil/Japanese later:** candidates are Whisper large-v3/turbo (99 languages), Qwen3-ASR (52 languages) or SenseVoice (zh/en/ja/ko/yue). All are available in sherpa-onnx. The engine interface should allow per-language routing.
- **Long-form:** Rflow runs full context. TDT v2's card supports 24 min with full attention. For dictation, the 3 min / 23 s case is compute-bound rather than accuracy-bound. VAD-based chunking into 15–30 s segments with parallel decode, or incremental decoding during recording, cuts perceived latency more than a model change would.
- **Ensembling / GER:** ROVER over two engines, or LLM rescoring of N-best, is plausible in principle, since sherpa MBS yields multiple hypotheses and Rflow already runs an LLM cleanup. A cheaper version is to pass the "Your words" list plus the 1-best to the existing LLM. No sourced CPU cost or benefit numbers were found.
